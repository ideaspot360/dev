## 1. Failure Scenario: Concurrent Inserts Colliding on Distinct Primary Keys

In an order ingestion pipeline under 3,200 requests/sec, concurrent transactions began throwing `MySQLTransactionRollbackException: Deadlock found when trying to get lock; try restarting transaction` (Error Code 1213, SQLSTATE 40001) [Source: MySQL 8.0 InnoDB Deadlocks](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks.html).

Engineers inspecting the transaction parameters were confused: Transaction 1 attempted to insert row `id = 502`, while Transaction 2 attempted to insert row `id = 508`. Because the two operations operated on mutually distinct primary keys, naive intuition suggested that row-level locking would execute concurrently without contention.

However, prior to issuing the `INSERT`, the business logic executed an application-level uniqueness pre-check to verify whether any order IDs had already been claimed in the current allocation batch (orders $[501, 510]$ after the last committed record $id = 500$):

```sql
-- Transaction 1
START TRANSACTION;
SELECT id FROM orders WHERE id BETWEEN 501 AND 510 FOR UPDATE;
INSERT INTO orders (id, user_id, order_no, status, created_at) 
VALUES (502, 1082, 'ORD-20261109-01', 'PENDING', NOW());
COMMIT;
```

```sql
-- Transaction 2
START TRANSACTION;
SELECT id FROM orders WHERE id BETWEEN 501 AND 510 FOR UPDATE;
INSERT INTO orders (id, user_id, order_no, status, created_at) 
VALUES (508, 1083, 'ORD-20261109-02', 'PENDING', NOW());
COMMIT;
```

Under MySQL's default `REPEATABLE READ` isolation level, the interaction between range locking and row insertion triggers a fatal cycle within the InnoDB lock manager.

## 2. Root Cause Analysis: Deep Dive into Gap Locks, Next-Key Locks & Insert Intentions

To understand why this deadlock occurs, we must trace how the InnoDB storage engine implements concurrency control and phantom read prevention on B-tree index pages [Source: MySQL 8.0 InnoDB Locking](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html).

### 2.1 The Four InnoDB Record Lock Types

InnoDB does not merely lock rows; it locks physical records within index B-trees and the spaces between them:

1. **Record Lock (`X,REC_NOT_GAP`)**: Locks the index record itself. It does not protect the gap before or after the record.
2. **Gap Lock (`X,GAP`)**: Locks the gap *before* an index record (or the gap before the pseudo-record `supremum` for intervals extending to infinity). Its sole purpose is to prevent concurrent transactions from inserting new rows into that specific range.
   * **Physical Anchoring**: In InnoDB's physical B-tree leaf layout, a gap lock does not float freely in memory; it is physically anchored to the lock bitmap of the index record that immediately follows the gap [Source: MySQL 8.0 Reference Manual](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html). For intervals extending beyond the maximum existing primary key, InnoDB anchors the gap lock to the **`supremum` pseudo-record** (a reserved record on the leaf page representing $+\infty$).
   * **Crucial Rule**: *Gap locks are purely non-conflicting with other gap locks*. A shared gap lock (`S,GAP`) and an exclusive gap lock (`X,GAP`) perform identically. Two concurrent transactions can hold conflicting exclusive gap locks on the exact same gap without blocking each other [Source: MySQL 8.0 InnoDB Locking](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html).
3. **Next-Key Lock (`X`)**: A compound lock consisting of a Record Lock on the index entry combined with a Gap Lock on the gap immediately preceding that record:
   $$\text{Next-Key Lock on } R_k = \text{Gap Lock on } (R_{k-1}, R_k) + \text{Record Lock on } R_k$$
   In `REPEATABLE READ`, InnoDB uses Next-Key Locks as its default mechanism for index scans to enforce Serializable Phantom Read guarantees.
4. **Insert Intention Lock (`X,GAP,INSERT_INTENTION`)**: A specialized gap lock requested by an `INSERT` statement prior to placing a row into an index gap [Source: MySQL 8.0 Data Locks Table](https://dev.mysql.com/doc/refman/8.0/en/data-locks-table.html).
   * Unlike standard gap locks, insert intention locks are compatible with each other. Two transactions can hold insert intention locks on the same interval simultaneously, provided their target insertion points are distinct.
   * However, **an Insert Intention Lock is strictly blocked by an existing Gap Lock or Next-Key Lock** held by another transaction on that same interval.

### 2.2 Lock Compatibility Matrix

The mathematical compatibility rules enforced by the InnoDB lock subsystem are summarized below [Source: MySQL 8.0 Reference Manual](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html):

| Held Lock (Row) \ Requested Lock (Col) | Gap Lock (`X,GAP`) | Record Lock (`X,REC_NOT_GAP`) | Next-Key Lock (`X`) | Insert Intention (`X,GAP,INSERT_INTENTION`) |
| :--- | :---: | :---: | :---: | :---: |
| **Gap Lock (`X,GAP`)** | **Compatible** | **Compatible** | **Compatible** | **CONFLICT (WAITING)** |
| **Record Lock (`X,REC_NOT_GAP`)** | **Compatible** | **CONFLICT (WAITING)** | **CONFLICT (WAITING)** | **Compatible** |
| **Next-Key Lock (`X`)** | **Compatible** | **CONFLICT (WAITING)** | **CONFLICT (WAITING)** | **CONFLICT (WAITING)** |
| **Insert Intention (`X,GAP,INSERT_INTENTION`)** | **Compatible** | **Compatible** | **Compatible** | **Compatible** |

### 2.3 The Deadlock State Sequence

Consider the existing primary keys in `orders`: record $R_1 = 500$ and record $R_2 = 515$. The gap between them is the open interval $(500, 515)$.

```text
Index State:  [ ... ] -> [ 500 ] -------- GAP (500, 515) --------> [ 515 ] -> [ ... ]
                                    ^               ^
                               Target 502      Target 508
```

1. **Step $t_1$ (Trx 1 Range Lock)**:
   Transaction 1 issues `SELECT id FROM orders WHERE id BETWEEN 501 AND 510 FOR UPDATE;`.
   Because the last committed order was $R_1 = 500$, no record exists with $id \in [501, 510]$. InnoDB navigates the clustered index B-tree and scans forward to the first existing record beyond the search boundary, which is $R_2 = 515$. Because record 515 does not match the predicate condition ($515 > 510$), InnoDB does not lock record 515 itself; instead, it places an exclusive **Gap Lock on $(500, 515)$** anchored to record 515 (`LOCK_MODE = X,GAP`, `LOCK_DATA = 515`).
2. **Step $t_2$ (Trx 2 Range Lock)**:
   Transaction 2 executes the same range query. Because Gap Locks are mutually compatible (Gap-Gap conflict = False), Transaction 2 is immediately granted an overlapping **Gap Lock on $(500, 515)$**. Neither transaction blocks on an existing row because no row in $[501, 510]$ was present.
   *Both transactions now concurrently hold an exclusive Gap Lock on $(500, 515)$*.
3. **Step $t_3$ (Trx 1 Insert Attempt)**:
   Transaction 1 executes `INSERT INTO orders VALUES (502, ...)`.
   To insert at $502 \in (500, 515)$, InnoDB requests an **Insert Intention Lock** on the gap before $515$.
   Looking up the compatibility matrix: Trx 2 holds a Gap Lock on $(500, 515)$.
   *Result*: Trx 1 is blocked. It transitions to `LOCK_STATUS = WAITING` waiting for Trx 2 to release its Gap Lock.
4. **Step $t_4$ (Trx 2 Insert Attempt)**:
   Transaction 2 executes `INSERT INTO orders VALUES (508, ...)`.
   To insert at $508 \in (500, 515)$, Trx 2 requests an **Insert Intention Lock** on the gap before $515$.
   Looking up the compatibility matrix: Trx 1 holds a Gap Lock on $(500, 515)$.
   *Result*: Trx 2 is blocked. It transitions to `LOCK_STATUS = WAITING` waiting for Trx 1 to release its Gap Lock.
5. **The Cyclic Deadlock**:
   $$T_1 \xrightarrow{\text{waiting for } T_2 \text{ to release Gap Lock on } (500, 515)} T_2 \xrightarrow{\text{waiting for } T_1 \text{ to release Gap Lock on } (500, 515)} T_1$$
   The circular wait-for graph is closed. InnoDB's background deadlock detector traverses the graph [Source: MySQL 8.0 InnoDB Deadlock Detection](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlock-detection.html), identifies the cycle, calculates transaction weights based on undo log volume, selects Transaction 1 as the victim, and issues an immediate rollback:
   ```text
   *** WE ROLL BACK TRANSACTION (1)
   ```

## 3. Common Missteps & Why Naive Fixes Failed

When deadlocks strike under high write concurrency, engineering teams frequently implement intuitive workarounds that either aggravate the issue or compromise system availability.

### Misstep 1: Blind Application Retries in Application Services

A common reaction is wrapping database calls in retry loops using Spring Retry or resilience libraries:

```java
// Anti-pattern: Blind retries amplify gap contention
@Retryable(
    retryFor = { MySQLTransactionRollbackException.class, DeadlockLoserDataAccessException.class },
    maxAttempts = 5,
    backoff = @Backoff(delay = 50, multiplier = 1.5)
)
public void createOrderWithRetry(Order order) {
    orderRepository.createOrder(order);
}
```

* **Why It Fails**: Under high load (3,200 RPS), retrying does not resolve the structural lock collision. Instead, rolled-back transactions immediately re-enter the lock wait queue, re-acquiring gap locks and colliding with newly arriving requests. This creates an exponential backlog:
  $$\text{Queue Length} \propto \text{RPS} \times \text{Attempts}$$
  HikariCP connection pool threads become saturated waiting for lock resolution, inflating $P_{99}$ latency from 34ms to over 2,800ms and cascading into upstream `HTTP 504 Gateway Timeout` errors.

### Misstep 2: Disabling Deadlock Detection or Increasing Lock Wait Timeouts

Another misguided attempt involves modifying MySQL server parameters to bypass deadlock detection overhead:

```diff
# /etc/mysql/mysql.conf.d/mysqld.cnf
[mysqld]
- innodb_deadlock_detect = ON
- innodb_lock_wait_timeout = 50
+ # Flawed workaround: Disabling deadlock detector
+ innodb_deadlock_detect = OFF
+ innodb_lock_wait_timeout = 120
```

* **Why It Backfires**: When `innodb_deadlock_detect = OFF`, InnoDB stops traversing the wait-for graph [Source: MySQL 8.0 Deadlock Detection Parameters](https://dev.mysql.com/doc/refman/8.0/en/innodb-parameters.html#sysvar_innodb_deadlock_detect). Transactions involved in circular gap lock dependencies are no longer terminated immediately; instead, they freeze until `innodb_lock_wait_timeout` elapses.
  With the timeout set to 120 seconds, active database connections remain pinned, rapidly exhausting the `max_connections` pool and taking down the entire database instance [Source: MySQL 8.0 Lock Wait Timeout Reference](https://dev.mysql.com/doc/refman/8.0/en/innodb-parameters.html#sysvar_innodb_lock_wait_timeout).

### Misstep 3: Coarse Distributed Locks or MySQL Table Locks

Some teams attempt to serialize inserts using Redis distributed locks or MySQL table locks:

```sql
-- Anti-pattern: Global table locking destroys write throughput
LOCK TABLES orders WRITE;
INSERT INTO orders VALUES (...);
UNLOCK TABLES;
```

* **Why It Backfires**: Serializing table writes eliminates gap deadlocks at the cost of catastrophic throughput degradation. In benchmarks on an 8-core database server, write throughput collapsed from 3,200 transactions/sec to 82 transactions/sec, introducing severe application thread pool starvation.

## 4. Before vs After Remediation: The Dual Production Fix

Resolving gap lock deadlocks requires a dual approach: tuning the database transaction isolation level and refactoring speculative application queries into atomic operations.

### Approach 1: Engine Isolation Tuning — Transitioning to `READ COMMITTED`

In write-heavy OLTP workloads, Gap Locking in `REPEATABLE READ` introduces severe concurrency bottlenecks. Transitioning the database engine to `READ COMMITTED` completely disables gap locking during search and index scans [Source: MySQL 8.0 Transaction Isolation Levels](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html).

* Under `READ COMMITTED`, InnoDB acquires only **Record Locks (`X,REC_NOT_GAP`)** for matching rows. Gap locks are disabled for standard searches and index scans.
* **Prerequisite**: Row-Based Binary Logging (`binlog_format = ROW`) is strictly required to prevent replication inconsistencies [Source: MySQL 8.0 Reference Manual](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html). (Note: `binlog_format` is officially deprecated as of MySQL 8.0.34 in anticipation of MySQL 8.4 LTS, where `ROW` is the mandatory default).

```diff
# /etc/mysql/mysql.conf.d/mysqld.cnf
[mysqld]
- transaction-isolation = REPEATABLE-READ
+ transaction-isolation = READ-COMMITTED
+ binlog_format = ROW
+ binlog_row_image = FULL
+ innodb_print_all_deadlocks = ON
```

Verify dynamic runtime application without database restart using MySQL 8.0 `SET PERSIST` (which records variables into `mysqld-auto.cnf` across daemon restarts):

```sql
SET PERSIST transaction_isolation = 'READ-COMMITTED';
SET GLOBAL binlog_format = 'ROW';
```

### Approach 2: Query Refactoring — Replacing Speculative Range Locks with Atomic Idempotency

Instead of executing speculative `SELECT ... FOR UPDATE` queries that lock non-existent index gaps, applications should rely on unique constraints and atomic upsert operations [Source: MySQL 8.0 Reference Manual](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html):

```diff
--- a/src/main/java/com/ideaspot360/shop/order/OrderRepository.java
+++ b/src/main/java/com/ideaspot360/shop/order/OrderRepository.java
@@ -24,20 +24,19 @@ public class OrderRepository {
     public Order createOrder(Order order) {
-        // FLAWED APPROACH: Speculative range check under REPEATABLE READ acquires gap locks
-        String checkSql = "SELECT id FROM orders WHERE id BETWEEN ? AND ? FOR UPDATE";
-        List<Long> existingIds = jdbcTemplate.queryForList(checkSql, Long.class, 501L, 510L);
-        if (!existingIds.isEmpty() && existingIds.contains(order.getId())) {
-            throw new DuplicateOrderException("Order ID collision detected");
-        }
-        String insertSql = "INSERT INTO orders (id, user_id, order_no, status, created_at) VALUES (?, ?, ?, ?, ?)";
-        jdbcTemplate.update(insertSql, order.getId(), order.getUserId(), order.getOrderNo(), order.getStatus(), order.getCreatedAt());
+        // PRODUCTION FIX: Atomic idempotency utilizing modern MySQL 8.0 row alias syntax
+        String upsertSql = """
+            INSERT INTO orders (id, user_id, order_no, status, created_at)
+            VALUES (?, ?, ?, ?, ?) AS new_orders
+            ON DUPLICATE KEY UPDATE
+                status = new_orders.status,
+                created_at = new_orders.created_at
+            """;
+        jdbcTemplate.update(upsertSql, order.getId(), order.getUserId(), order.getOrderNo(), order.getStatus(), order.getCreatedAt());
         return order;
     }
 }
```

#### Modern MySQL 8.0 Alias Syntax & Deep Locking Mechanics
1. **Modern Row Alias Syntax (`AS new_orders`)**: In MySQL 8.0.20+, referencing columns via `VALUES(col_name)` in `ON DUPLICATE KEY UPDATE` is formally deprecated (`ER_WARN_DEPRECATED_SYNTAX_NO_REPLACEMENT`) [Source: MySQL 8.0 Reference Manual — INSERT ... ON DUPLICATE KEY UPDATE Statement](https://dev.mysql.com/doc/refman/8.0/en/insert-on-duplicate.html). The modern standard declares a row alias after the `VALUES` clause (`VALUES (...) AS new_orders`) and accesses incoming fields directly (`new_orders.status`).
2. **Clustered Primary Key vs Unique Secondary Index Locking**:
   Under MySQL's internal lock rules [Source: MySQL 8.0 Reference Manual — Locks Set by Different SQL Statements in InnoDB](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html):
   * When an `ON DUPLICATE KEY UPDATE` collision occurs on the clustered **PRIMARY KEY**, InnoDB acquires an **exclusive record-only lock (`X,REC_NOT_GAP`)** on the existing row, introducing zero gap locks.
   * When a duplicate collision occurs on a **UNIQUE SECONDARY KEY** (`uk_order_no`), InnoDB acquires an **exclusive Next-Key Lock (`X`)**, locking both the secondary index record and the preceding gap.
   * **Foreign Key & Duplicate Checks under `READ COMMITTED`**: While `READ COMMITTED` eliminates gap locking for regular search queries and index scans, InnoDB **explicitly retains gap locking for duplicate-key checks and foreign-key constraint validations** [Source: MySQL 8.0 Reference Manual — Transaction Isolation Levels](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html). Removing speculative range pre-checks ensures that standard insert flows operate exclusively with atomic record locks, completely eliminating the circular gap lock wait graph.

By removing the range scan, no gap locks are placed on $(500, 515)$. Each transaction directly executes its atomic insert. When unique record insertions occur without artificial gap scans, lock acquisition proceeds in sub-millisecond execution cycles.
